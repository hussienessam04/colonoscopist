# Fix language persistence on restart; fix NotoSansArabic ENOENT; second translation sweep

## Task 1 — Fix language persistence on app restart

**Files:**
- `src/renderer/src/i18n/index.ts` (single-line edit)

**Action:**

Root cause: `src/renderer/src/i18n/index.ts:30` orders detectors as `['htmlTag', 'localStorage', 'navigator']`. The `htmlTag` detector reads `<html lang>` from `src/renderer/index.html` which hardcodes `lang="en"` (verified — the file has `<html lang="en" dir="ltr">` and the language detector runs BEFORE React mounts), so `htmlTag` ALWAYS wins on every boot — the localStorage value the doctor saved when they picked AR is never consulted, and the renderer paints EN + LTR for one frame before `<LanguageApplier />` flips dir/lang via `useEffect`.

Fix: swap the order to `['localStorage', 'htmlTag', 'navigator']`. localStorage wins if present (the saved operator choice); `htmlTag` is the fallback for first-launch (when localStorage is empty, htmlTag reads the en default from index.html, which is correct). No other change needed — the `caches: ['localStorage']` flag already persists whatever the detector resolves to, so the second boot and beyond keep winning with the saved value.

`useLanguage()` in `src/renderer/src/main.tsx` is wired via `<LanguageApplier />` rendered BEFORE `<App />` inside `<React.StrictMode>` (verified — main.tsx:28-29 mounts `<LanguageApplier />` first in the tree, so `useLanguage()`'s `useEffect` fires before App paints). The dir/lang flip therefore lands on the same render pass as the language detection resolution, so no second render ever shows the wrong direction.

**Verify:**
- Open the app, switch language to AR (Settings → Profile or via devtools `localStorage.setItem('i18nextLng', 'ar')`).
- Verify `localStorage.getItem('i18nextLng') === 'ar'`.
- Quit the app fully (Electron reload), reopen. On first paint, `<html dir>` is `'rtl'` and `<html lang>` is `'ar'`. The login/welcome screen reads in Arabic immediately.
- Negative test: clear localStorage (`localStorage.removeItem('i18nextLng')`), reload — falls back to EN (the `<html lang="en">` default in index.html).

**Done:**
- App restart honors the saved language from localStorage. Switching to AR persists across full app restarts.

## Task 2 — Fix NotoSansArabic font ENOENT after shared storage

**Files:**
- `src/main/pdf/render-report-pdf.ts` (single function — multi-location path fallback)

**Action:**

Root cause: `src/main/pdf/render-report-pdf.ts:94` does `path.join(__dirname, 'fonts', 'NotoSansArabic-Regular.ttf')`. The comment above (lines 89-93) claims "In dev __dirname is the source-tree src/main/pdf/" — that is FALSE for electron-vite. Verified: `electron.vite.config.ts` (lines 11-15) emits `src/main/*` into `out/main/index.js`, and Electron loads main from `out/main/`. In BOTH dev and prod `__dirname` resolves to `out/main/`. The TTF lives at `src/main/pdf/fonts/NotoSansArabic-Regular.ttf` (verified — the directory exists with the file in it) and is never copied to `out/main/fonts/`. Result: `fs.readFileSync` inside `@react-pdf/renderer`'s Font.register throws ENOENT when the AR report tries to finalize. The graceful degrade (`_notoArabicAvailable = false` in the catch) means the AR report silently renders with Helvetica instead of NotoSansArabic — AR glyphs render as `tofu` boxes.

Ponytail fix: skip the build-script / extraResources / predev hook entirely. Use a multi-location path fallback at the call site — `fs.existsSync` is 4 lines, no new npm script, no new lifecycle hook, no `electron-builder` config change, no test seams for the copy script. The renderer doesn't care which path wins as long as Font.register gets a real TTF.

Replace the single `ttfPath = path.join(__dirname, 'fonts', 'NotoSansArabic-Regular.ttf')` line with a small lookup that tries:

1. `path.join(__dirname, 'fonts', 'NotoSansArabic-Regular.ttf')` — the canonical path that future extraResources / copy hooks will populate. Resolves to `out/main/fonts/NotoSansArabic-Regular.ttf` today (doesn't exist yet but the lookup is forward-compatible).
2. `path.join(__dirname, '..', '..', 'src', 'main', 'pdf', 'fonts', 'NotoSansArabic-Regular.ttf')` — dev fallback that resolves from `out/main/` back to `src/main/pdf/fonts/`. Verified math: `out/main/` → `out/` → project root → `src/main/pdf/fonts/`. Exists today.
3. (Optional) `path.join(__dirname, '..', '..', '..', 'src', 'main', 'pdf', 'fonts', 'NotoSansArabic-Regular.ttf')` — covers the asarUnpack shape if main is later moved under `app.asar/` (one extra `..` to escape the asar prefix). Skip this one in v1 — YAGNI; the dev fallback already proves the layout, and `fs.existsSync` makes future extension a one-liner.

Use `fs.existsSync` to pick the first that exists; if NONE exist, keep the existing `try/catch` so `_notoArabicAvailable = false` triggers the Helvetica degrade (do not change behavior for the "no fonts at all" edge case — the IPC contract still holds, the report still writes, AR glyphs still tofu as today).

Also rewrite the stale comment block (lines 89-93) so it doesn't lie to the next reader. State plainly: "electron-vite emits main/* into out/main/, so __dirname is out/main/ regardless of dev/prod. The font lives at src/main/pdf/fonts/ in source; we resolve the canonical path first (forward-compatible with a future copy step / extraResources), then fall back to the dev source tree."

Add a `// ponytail:` comment naming the ceiling: "if the build is ever run as an ASAR bundle, the dev fallback may break under `app.asar/` — add a third path join at that time, no other change."

**Verify:**
- `npm run typecheck` passes (no new TS errors from the import).
- In dev: `npm run dev`, set language to AR in profile, create a procedure + finalize a report. The PDF writes successfully (no ENOENT in the main-process console). Open the rendered PDF — Arabic text renders with proper NotoSansArabic glyphs (no tofu).
- In production build: `npm run build`, run `electron-vite preview`, repeat the AR-finalize flow. PDF writes successfully.
- Negative test: temporarily move both TTF paths away (e.g. `mv src/main/pdf/fonts out/`). The catch handler kicks in, `_notoArabicAvailable` becomes false, the AR report still writeable (Helvetica fallback), console logs `NotoSansArabic TTF registration failed`. Restore the font dir afterwards.

**Done:**
- Finalizing an AR-language report no longer throws ENOENT. The TTF resolves from the dev source tree today, and the canonical `out/main/fonts/` path is wired for future build-script fixes.
