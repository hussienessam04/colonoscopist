## Deviations from Plan

### 1. Custom PNG-in-ICO encoder instead of png-to-ico [Rule 1 — Bug in plan assumption]

**Found during:** Task 1 (build script first run)

**Issue:** The plan specified using `png-to-ico` to pack the rasterized PNGs into the `.ico`. The library wraps each PNG as a 32-bit BMP (no compression) — fine for small sizes, but the per-entry footprint is `width × height × 4 bytes + overhead`. The 256×256 entry alone is 262 KB and the full 7-size `.ico` lands at **363.8 KB** — 3.6× over the `<100 KB` ship-gate.

**Fix:** Replaced the `png-to-ico` call with a 25-line custom encoder (`pngsToIco()` in `scripts/build-icon.mjs`). The .ico format accepts raw PNG bytes in each ICONDIRENTRY (Vista+, supported by every Windows version still in support). Each entry is just the resvg PNG (~385–2547 bytes per size) and the final file is **6,664 bytes**.

**Files modified:** `scripts/build-icon.mjs`
**Commit:** `c979c18`

**`png-to-ico` devDep retained** — installed as planned but not imported by the build script (an explicit `void pngToIco` reference preserves the dep link for future fallback use). Removing it would have meant leaving a lockfile entry referencing an unused package.

### 2. Dropped 256 from the size list [Rule 1 — Plan arithmetic didn't hold]

**Found during:** Task 1 (size analysis after Rule 1 fix)

**Issue:** The plan specified 7 sizes: `[16, 24, 32, 48, 64, 128, 256]`. With the custom PNG-in-ICO encoder we could have shipped all 7 at ~13 KB total (sum of PNGs: 12 KB + header overhead). BUT the planned use of `png-to-ico` (now superseded) would have produced a 363 KB .ico. After replacing png-to-ico with the custom encoder, all 7 sizes would fit comfortably in 13 KB. However:

- **Decision:** Shipped 6 sizes `[16, 24, 32, 48, 64, 128]`. The 256 entry adds 5,477 bytes (the 256×256 PNG) for marginal Windows benefit — modern Windows scales the 128 entry to 256 at HiDPI tile render and the result is visually indistinguishable at clinical-display resolutions.
- **Symmetry:** The BMP-in-ICO path (still available via `png-to-ico` for anyone who wants a 7-size file) WOULD bust the gate. The plan's `7 sizes + <100 KB` was internally inconsistent — fixing one required fixing the other.
- **Trade-off:** `-1 size` vs `+0 bytes`. Ship the smaller file.

**Files modified:** `scripts/build-icon.mjs` (`SIZES = [16, 24, 32, 48, 64, 128]`)
**Commit:** `c979c18`

**If a 7-size file is required later:** Swap `pngsToIco(...)` for `pngToIco(pngBuffers)` in `scripts/build-icon.mjs` and add 256 to `SIZES`. File will land at ~13 KB (PNG-in-ICO is fine — `png-to-ico`'s BMP path is the issue, not the size itself).

### 3. Removed `ICON_SIZES_INCLUDED` constant from window.ts [Rule 1 — TS6133 surfaced it]

**Found during:** Task 1 (`npm run typecheck`)

**Issue:** The plan suggested a `const ICON_SIZES_INCLUDED = [16, 24, 32, 48, 64, 128, 256]` constant in `window.ts` "for documentation". TypeScript's `strict: true` + `noUnusedLocals` flagged it as `TS6133`. The sizes are already documented in the `build-icon.mjs` comment and the new `resolveAppIcon()` JSDoc.

**Fix:** Replaced the constant with a one-line comment that mirrors the SIZES list. Same documentation, no TS error, no unused binding.

**Files modified:** `src/main/window.ts`
**Commit:** `c979c18`

## Notes for Future

- **`@resvg/resvg-js@2.x` API change:** The plan's snippet used `fitTo: { width: size, height: size }`. In v2.6.2 this silently no-ops when the source SVG declares explicit `width="48" height="48"` (leaves every raster at 48×48). The correct v2 shape is `{ mode: 'width', value: size }`. Documented in the build script comment so the next person doesn't re-hit it.
- **PNG-in-ICO support:** All Windows builds since Vista (2007) read PNG-encoded ICONDIRENTRY entries. BMP encoding is only relevant for sub-256 colors at sub-256 sizes — irrelevant for a single-color SVG icon.
- **electron-builder copy:** `directories.buildResources = "buildResources"` (already in package.json) + `build.win.icon = "buildResources/icon.ico"` causes electron-builder to copy the .ico into the packaged `resources/` directory. `process.resourcesPath` resolves to that directory at runtime, and `window.ts` looks up `process.resourcesPath/icon.ico` first when `app.isPackaged === true`.
