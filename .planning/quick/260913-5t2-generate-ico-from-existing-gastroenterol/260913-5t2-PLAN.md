# Quick task — Generate real .ico from existing gastroenterology SVG

## Context

The Colonoscopist Windows desktop app currently ships with a brand-tinted gastroenterology SVG (`src/renderer/public/icon.svg`, CC0 from healthicons.org, fill `#0E3A47`). It works for:

- Browser-tab favicon (renderer reads `/icon.svg` via Vite's `public/` copy)
- `BrowserWindow` icon on Windows (Electron 32 / Chromium 128+ render SVG, but it's fragile — depends on Chromium's image decoder)

It does NOT work for:

- Windows `.exe` icon — electron-builder requires a real `.ico` (multi-resolution BMP/PNG bundle) for the NSIS installer, portable EXE, and desktop shortcut
- BrowserWindow fallback on older Chromium image paths

Per a prior deferral (`260913-4qz-CONTEXT.md` — "Out of scope: Windows .exe icon (.ico)"), we're now closing that gap with the smallest toolchain possible.

**Why not Playwright/sharp/ImageMagick?** They spin up heavy machinery (Chromium / native image libs) for a one-shot rasterization. `resvg-js` is the industry standard — pure WASM, ~3 MB, no native build step, used by Vite/esbuild internally. `png-to-ico` bundles the PNGs into one multi-resolution `.ico`. Both are pure-JS devDependencies, only loaded at build time.

**Visual:** Identical to the existing SVG. The script just rasterizes the brand-tinted gastroenterology mark at 7 sizes (16/24/32/48/64/128/256 px) and packs them into one `.ico`.

## Files to read

- `src/renderer/public/icon.svg` — the brand-tinted source SVG (already CC0 + teal)
- `src/main/window.ts` — current `resolveAppIcon()` helper (probes SVG paths only)
- `package.json` — scripts (`build`), `build` block (`directories.buildResources = "buildResources"`, no `win.icon`), devDependencies
- `.gitignore` — no `buildResources/` rule yet (we'll keep the `.ico` tracked per the spec's "first-cut" recommendation)
- `scripts/` — existing build helpers are `.cjs`; this task uses `.mjs` (forced ESM regardless of package.json `type`)

## Out of scope

- Code signing, auto-update, Linux/Mac targets, `.icns` / Linux `.png` — Windows-only this round
- Dev-mode HMR for the icon (the script is a build-time tool, not a runtime watcher)
- A designer polish pass on the icon mark itself

## Task 1 — Build script + electron-builder wiring + window.ts resolver

**Files:**

- `scripts/build-icon.mjs` (new — ESM build script)
- `buildResources/.gitkeep` (new — keep the directory in git)
- `package.json` (add 2 devDeps + `build:icon` script + extend `build` script + add `build.win.icon`)
- `src/main/window.ts` (extend `resolveAppIcon()` to probe `.ico` first when packaged)

**Action:**

### 1a. `scripts/build-icon.mjs`

New ESM script (`.mjs` forces ESM regardless of root `type`):

- Resolve paths with `node:path` and `node:fs/promises`:
  - `SRC = path.resolve('src/renderer/public/icon.svg')`
  - `OUT_DIR = path.resolve('buildResources')`
  - `OUT = path.join(OUT_DIR, 'icon.ico')`
- Sizes: `[16, 24, 32, 48, 64, 128, 256]`.
- Read SVG with `await fs.readFile(SRC)`. Build PNG buffers via `@resvg/resvg-js`:
  ```js
  import { Resvg } from '@resvg/resvg-js';
  const resvg = new Resvg(svgBuffer, { fitTo: { width: size, height: size } });
  const png = resvg.render().asPng();
  ```
  (Ponytail: `asPng()` is the stdlib-equivalent — no extra encoding config needed.)
- Build the `.ico` via `png-to-ico`:
  ```js
  import pngToIco from 'png-to-ico';
  const ico = await pngToIco(pngBuffers); // png-to-ico accepts an array of PNG buffers
  ```
- `await fs.mkdir(OUT_DIR, { recursive: true })`, then `await fs.writeFile(OUT, ico)`.
- Print `Wrote ${OUT} (${kb} KB, ${sizes.length} sizes)` on success.
- Wrap top-level body in a `try/catch` that prints the error and exits with code 1 on failure.
- Idempotency: read the SVG mtime once. If `OUT` exists and `OUT.mtimeMs >= SRC.mtimeMs`, skip and print `Up to date`. Cheap, no hash needed — if the SVG changes, the `.ico` gets rebuilt.
- `import` at top, all code inside `async function main()` invoked at the bottom (no top-level await needed; clearer stack trace).

### 1b. `buildResources/.gitkeep`

Empty file. Comment on first line: `# electron-builder reads buildResources/icon.ico at packaging time. Keep this directory in git even when the .ico is regenerated.`

### 1c. `package.json`

- `devDependencies` — add two entries (use `^` to match project convention):
  - `"@resvg/resvg-js": "^2.6.2"` (current stable; check npm for the latest at install time)
  - `"png-to-ico": "^2.1.1"` (current stable)
- `scripts.build` — change from `"electron-vite build"` to `"npm run build:icon && electron-vite build"`. The `package` and `package:portable` scripts already invoke `npm run build` so they inherit the icon step.
- `scripts` — add `"build:icon": "node scripts/build-icon.mjs"` next to the existing `build` line.
- `build.win` — add `"icon": "buildResources/icon.ico"`. electron-builder copies this into the package resources at `resources/icon.ico` (no `extraResources` change needed; the default `buildResources` glob covers it).

### 1d. `src/main/window.ts`

Extend `resolveAppIcon()` so the resolution order is: `.ico` (packaged) → `.svg` candidates (existing) → undefined.

- Add `import { app, ... }` is already present — `app` is already imported.
- Add `const ICON_SIZES_INCLUDED = [16, 24, 32, 48, 64, 128, 256];` constant for documentation (not strictly required but matches the build script and makes the trace back to the .ico bundle obvious).
- Update the candidate list to:
  ```ts
  const candidates: string[] = [];
  if (app.isPackaged) {
    // electron-builder default: buildResources/icon.ico → resources/icon.ico
    candidates.push(path.join(process.resourcesPath, 'icon.ico'));
  }
  candidates.push(
    path.join(__dirname, '../renderer/icon.svg'),
    path.join(__dirname, '../renderer/assets/icon.svg'),
  );
  ```
- Replace the `fs.existsSync` probe + `nativeImage.createFromPath` loop. Keep the same fallback semantics: first hit wins; if `nativeImage.createFromPath()` returns an empty image (`isEmpty()`), keep looking — defensive against a stale `.ico` file that electron-builder copied but was empty/corrupt.
- Update the leading ponytail comment to mention the new resolution order (ICO first when packaged, SVG fallback for dev).
- Note in the comment that `app.isPackaged === false` in dev (current behavior continues — SVG fallback for `npm run dev`, no change visible to the dev loop).

**Verify:**

- `npm install` succeeds (adds 2 devDeps, no native rebuild needed — both are pure JS).
- `npm run build:icon` produces `buildResources/icon.ico` (5–30 KB target).
- File check: `test -f buildResources/icon.ico && wc -c buildResources/icon.ico` (or PowerShell equivalent on Windows).
- `npm run typecheck` — both `typecheck:node` and `typecheck:web` clean (the script is `.mjs`, no TS impact; `window.ts` change must compile).
- Quick grep gate: `grep -c "buildResources/icon.ico" package.json` (expect 1), `grep -c "build:icon" package.json` (expect ≥2 — script def + build chain).
- Idempotency: run `npm run build:icon` twice — second run prints "Up to date" and exits 0.

**Done:**

- `buildResources/icon.ico` exists on disk, ≥1 KB, <100 KB.
- `package.json` `devDependencies` lists `@resvg/resvg-js` and `png-to-ico`.
- `package.json` `scripts.build` chains `build:icon` before `electron-vite build`.
- `package.json` `build.win.icon` points to `buildResources/icon.ico`.
- `src/main/window.ts` `resolveAppIcon()` probes `process.resourcesPath/icon.ico` (when `app.isPackaged`) before the SVG candidates.
- `npm run typecheck` clean.
- Running the script twice prints "Up to date" the second time.

## Task 2 — Smoke: rasterize the .ico at every advertised size + visual sanity

**Files:** none (read-only verification)

**Action:**

Drop a one-off Node check inline via `node -e` (no new script file needed — this is a ponytail smoke, not a permanent test):

```bash
node -e "
import('@resvg/resvg-js').then(async ({ Resvg }) => {
  const fs = await import('node:fs/promises');
  const ico = await fs.readFile('buildResources/icon.ico');
  // .ico header: reserved(2) + type(2)=1 + count(2) at offset 4
  const count = ico.readUInt16LE(4);
  console.log('ICO entry count:', count, '(expected 7)');
  // Each ICONDIRENTRY is 16 bytes starting at offset 6; width byte (offset 6+i*16) is 0 for 256px
  const sizes = [];
  for (let i = 0; i < count; i++) {
    const off = 6 + i * 16;
    const w = ico.readUInt8(off) || 256;
    sizes.push(w);
  }
  console.log('Sizes:', sizes.sort((a,b)=>a-b).join('x') + ', ');
});
"
```

This proves the .ico file has the 7 advertised sizes baked into its ICONDIRENTRY headers — no decode / no display required. (Ponytail: stdlib `Buffer.readUInt16LE` is the right primitive; no extra dep.)

For visual verification, the user opens `buildResources/icon.ico` in Windows Explorer → Properties → preview pane. It must show the gastroenterology mark (teal `#0E3A47` colon + bowel shapes) at every size from 16×16 (taskbar pinned) to 256×256 (Desktop / Start tile). If a size is missing or shows the generic default, the script's `asPng()` output is being truncated — debug from there.

**Verify:**

- The `node -e` check prints `ICO entry count: 7 (expected 7)` and `Sizes: 16,24,32,48,64,128,256`.
- Open the .ico in Windows Explorer (or any image viewer that reads .ico) — every size shows the gastroenterology mark, not the default Chromium icon.

**Done:**

- ICONDIRENTRY count = 7.
- ICONDIRENTRY widths = `[16, 24, 32, 48, 64, 128, 256]` (width byte 0 → 256).
- User has eyeballed the .ico in Explorer and confirmed the mark renders at all sizes.
