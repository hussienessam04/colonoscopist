# Phase 2 Plan 01 — Database foundation + auth + audit + users infrastructure

## Objective

Ship the SQLite data layer (open, migrations, WAL, audit triggers), the PIN-based auth IPC (status, bootstrap, login, logout, users-list, recovery-request), the users management IPC (create, remove, reset-pin), the audit log helper, the in-memory session state, and the Vitest test scaffolding. The renderer wiring for the wizard + login + patient list + settings users ships in Plan 02-03.

**User story (MVP mode):** *As a clinic that runs the app for the first time, I want to create an admin user and a clinic name through a wizard so that the workstation is ready for daily login without any cloud setup.*

Persist as `scrypt$N$r$p$saltB64$hashB64`. `verifyPin` uses `timingSafeEqual` over equal-length buffers. Wrap both via `safeStorage.encryptString` / `safeStorage.decryptString` so the on-disk value is DPAPI-encrypted at rest; if `safeStorage.isEncryptionAvailable()` is false, log a warning and store plaintext (acceptable for v1 Linux-only gap; Windows is the target).

## Threat Model

| Threat | STRIDE | ASVS | Mitigation |
|--------|--------|------|------------|
| Brute-force 4-digit PIN (10k space) | Spoofing | V2 | Exponential backoff `1s, 2s, 4s, 8s, 16s` capped at 60s; 10th failure → indefinite `locked_until = null` (admin reset only) — per PITFALLS §Pitfall 5 |
| Tampering `audit_log` to hide activity | Tampering | V8 | SQL triggers `audit_log_no_update` + `audit_log_no_delete` raising `ABORT`; no `audit:update` / `audit:delete` IPC channels; append-only verified by `tests/main/audit/append-only.test.ts` |
| `pin_hash` stolen from disk → offline crack | Information Disclosure | V6 | scrypt `N=2^15, r=8, p=1, maxmem=64MB` (~50ms per hash × 10k PINs = 8 min per attempt window before backoff) + `safeStorage.encryptString` DPAPI wrap at rest |
| First-launch admin self-exclusion (D-04) | Denial of Service | V11 | Wizard commit is a single `db.transaction(...)`; if any insert throws, the row is not created and the wizard re-prompts on next launch; on next boot `auth:bootstrap` retries on a fresh DB. The vendor recovery file is the escape hatch (Phase 8). |
| `nodeIntegration` drift in renderer | Elevation of Privilege | V10 | Phase 1 security baseline already enforced (`contextIsolation: true`, `nodeIntegration: false`, `sandbox: true`, `webSecurity: true`); the existing `tests/shell/auth-status.test.ts` invariant is unchanged |
| Self-induced admin lockout | Denial of Service | V2 | Admin can reset their own PIN via `users:resetPin` against `session.currentUserId` (the admin's own row) per D-03; the vendor recovery file is the escape hatch if the admin forgets the PIN entirely (D-04) |
| `metadata` JSON smuggling PII through audit | Information Disclosure | V8 | `audit()` helper API accepts `entityType` + `entityId` + structured counts only; no field values; enforced by code review rule + `tests/main/audit/every-mutation.test.ts` |
| Concurrent admin reset + lockout race | Denial of Service | V11 | `resetPin` is a single `UPDATE users SET failed_attempts = 0, locked_until = NULL, pin_hash = ?`; SQLite is single-writer; no TOCTOU |
| First-launch wizard returning misleading `auth:status` | Repudiation | V7 | `auth:bootstap` is the only path that creates the admin; the IPC contract returns the `UserPublic` (no `pin_hash`) so the renderer cannot prefill the wizard from a stale state |

## Must-Haves

### Truths
- DB opens at `<userData>/data/app.db` with WAL on first launch.
- Migrations run idempotently (second open is a no-op).
- `auth:bootstrap` commits the first admin user + `clinic_name` + `schema_version` + an `audit_log` row atomically.
- `auth:login` verifies the PIN via scrypt, applies exponential backoff, and locks the account after 10 failures.
- `audit_log` is append-only via SQL triggers; any UPDATE/DELETE attempt raises `ABORT`.
- `session.currentUserId` is `null` on boot and is never persisted.
- Lost admin PIN is recoverable via the Phase 2 UX surface (`auth:recoveryRequest` → `mailto:` to vendor with machine fingerprint), with the actual recovery file flow landing in Phase 8.

### Prohibitions
- **No hard delete on `users` or `patients`** — soft-delete via `deleted_at` only; no `DELETE` IPC.
- **No plaintext PIN at rest** — scrypt hash + `safeStorage.encryptString` wrap.
- **No UPDATE/DELETE on `audit_log`** — triggers + IPC reads only.
- **No persistent session across reboot** — `session` is in-memory only; `app.on('before-quit')` does not write it.
- **No `role` column in `users`** — locked single-admin model per D-02 (one-way schema decision; the absence is noted in `users.ts`).
- **No metadata field values in `audit_log`** — only `entityType` + `entityId` + structured counts.

### Key Links
- `src/main/ipc/auth.ts` → `src/main/auth/index.ts` → `src/main/db/users.ts` + `src/main/db/audit.ts` — every login code path funnels through `audit()` for AUTH-03.
- `src/main/db/migrations/0001_init.sql` ↔ `src/main/db/audit.ts` — the triggers refuse the only mutation channel audit has, so tampering is impossible at the SQL layer even if the app code is buggy.
- `src/main/auth/session.ts` → `src/main/auth/index.ts` (login/logout) — main-process session is the only auth state; the renderer mirrors it via `auth:status`.
