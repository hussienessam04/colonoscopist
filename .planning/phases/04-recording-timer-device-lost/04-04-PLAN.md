<objective>
Ship the device-lost detection + crash-recovery flows end-to-end: the ffmpeg stderr regex that recognizes a USB disconnect, the rename + sidecar JSON + audit + emit sequence that preserves the partial mp4 with its bounded last-known-timestamp metadata (per D-03), the renderer's inline `<Alert>` banner (no modal, per UX-Pitfalls) with formatted duration copy, the launch-time `scanForOrphans` walker that emits one audit row per orphan partial file (per D-04, idempotent), and the upgrade of `ProcedureReview` to wrap the partial status in a full shadcn `Alert`.

Purpose: D-03 keeps `status='recording'` after device-lost so the doctor can decide whether to Stop (finalizing as `status='partial'`) or wait; the partial mp4 + sidecar JSON are the recovery signal Phase 5 review consumes and Phase 7 backup preserves. D-04 ships the launch-time scan so the audit log records every orphan on next-boot, and Phase 7 cleanup owns deletion. The remaining reliability risk in Phase 4 (silent long-procedure crashes) is therefore bounded by the launch-time scanner + the rename-only partial-path convention.

Output: `device-lost.ts` (regex + helpers), `orphans.ts` (scanForOrphans body replaces the Plan 01 stub), the supervisor `enterDeviceLost()` branch on stderr match, the renderer `<DeviceLostBanner>` + ProcedureRoom + ProcedureReview partial-status upgrade, and the Wave 0 tests covering the regex + orphan scan + finalize-after-device-lost path.

## Trust Boundaries

| Boundary | Description |
|---|---|
| ffmpeg stderr -> supervisor `onStderr` | External process output parser; regex-tested for the device-lost signal. |
| Main -> filesystem rename | The supervisor is the ONLY writer of `.partial.mp4` / `.partial.mp4.json` (cap rule). |
| Renderer -> Zustand store `lastLost` | The renderer's lastLost slot is fed by the `'lost'` event from IPC; never written from a renderer-side action. |
| Launch-time scanner -> audit_log | `scanForOrphans` is main-side only; never reachable from the renderer. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|---|---|---|---|---|---|
| T-04-17 | Tampering | `device-lost.ts` regex over-strict | medium | mitigate | DEVICE_LOST_RE matches 6 substrings per PITFALLS §2 / RESEARCH.md §3; if a future doctor driver emits a new error phrase, the regex is updated in one place and the unit test (`tests/main/recorder/device-lost.test.ts` row 1) is extended in the same PR. |
| T-04-18 | Denial of Service | scanForOrphans on huge `data/media/patients` trees | medium | mitigate | The walk is depth-2 only and `--withFileTypes` so it never descends into segment files or patients with 1000+ procedures (clinic scale is <10k procedures per workstation per ARCHITALL §Scaling); the LIKE-on-metadata fingerprint dedup keeps audit_log inserts O(uniques). |
| T-04-19 | Information Disclosure | partial JSON content | low | mitigate | Sidecar JSON contains only { procedureId, lastKnownTimestampMs, deviceLostAt, deviceName } -- no procedure content, no patient metadata, no body notes (per Fix 6 inheritance). |
| T-04-20 | Tampering | orphan fingerprint dedup | low | mitigate | The fingerprint is `sha256(procedureId + ':' + lastKnownTimestampMs + ':' + sidecarContent).slice(0,16)`; an attacker would need to rewrite the sidecar JSON OR the procedureId/lastKnownTimestampMs to spoof a duplicate -- both fields are written server-side only, so the attack vector is internal.
