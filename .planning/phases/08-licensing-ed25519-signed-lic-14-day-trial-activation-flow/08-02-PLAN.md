    **1. Create `src/main/license/trial.ts`:**

    ```
    // Phase 8 / Plan 02 — trial clock reader (LIC-01).
    // Per CONTEXT D-01 + D-02: the trial clock lives on `settings.trial_started_at`.
    // The wizardBootstrap transaction writes the row once on the first launch
    // (no `ON CONFLICT UPDATE` per D-01 verbatim — first-write-wins). This
    // module READS the row on every boot — it never writes.
    //
    // The 14-day constant is inlined here (one source of truth); the renderer
    // computes the countdown from `LicenseStatus.trialDaysRemaining` which
    // is derived from `expiresAt - now` below. Per RESEARCH §Pattern 4 the
    // shape is the discriminated union that `status.ts:computeLicenseStatus()`
    // consumes.

    import { getDb } from '../db';

    const TRIAL_DURATION_MS = 14 * 24 * 60 * 60 * 1000;

    export type TrialState =
      | { state: 'trial'; daysRemaining: number; expiresAt: number }
      | null;

    export function readTrialStartedAt(): number | null {
      const row = getDb()
        .prepare(`SELECT value FROM settings WHERE key = 'trial_started_at'`)
        .get() as { value: string } | undefined;
      if (!row) return null;
      const parsed = parseInt(row.value, 10);
      if (!Number.isFinite(parsed) || parsed <= 0) return null;
      return parsed;
    }

    export function getTrialState(now: number = Date.now()): TrialState {
      const startedAt = readTrialStartedAt();
      if (startedAt === null) return null;
      const expiresAt = startedAt + TRIAL_DURATION_MS;
      const remaining = expiresAt - now;
      if (remaining <= 0) return null; // expired — falls through to 'expired' state in status.ts
      const daysRemaining = Math.ceil(remaining / (24 * 60 * 60 * 1000));
      return { state: 'trial', daysRemaining, expiresAt };
    }
    ```

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Wizard transaction ↔ audit log | Both writes happen inside the same `db.transaction`; partial failure rolls back both |
| Trial clock read ↔ status computation | `status.ts:computeLicenseStatus()` reads `getTrialState()` on every boot; the trial clock is NEVER used for license truth (per D-02 + PITFALLS §Pitfall 6) |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-08-T01 | Tampering | Trial clock manipulation via direct SQL | medium | mitigate | The verify path never trusts the trial clock — `verifyLicense` reads `settings.trial_started_at` only for display, NOT for permission (per CONTEXT D-02 verbatim: "The `license_is_valid` boolean does NOT live on `settings`"). The column is a clock, not a permission — manipulating it doesn't grant license validity. |
| T-08-T02 | Tampering | Trial-clock reset via reinstall | low | mitigate | Per D-01: `<userData>` persists across Electron app reinstalls (same app name = same path). The trial row survives reinstalls; a fresh DB starts a fresh 14-day window. Documented in the renderer's License sub-page FAQ (Plan 05). |
| T-08-T03 | Repudiation | Wizard transaction partial failure | medium | mitigate | The 5 original INSERTs + the new INSERT + the new audit row run inside ONE `db.transaction(() => { ... })`. If ANY statement throws, the entire transaction rolls back — no half-wizard state, no orphan trial row. The existing wizard.test.ts already covers this pattern. |
| T-08-T04 | Tampering | Sidecar `.lic` injection to bypass trial clock | high | mitigate (Plan 04) | Plan 04 ships `loadAndVerifyLicense` which is the ONLY way to set `state: 'licensed'`. The verify path reads the sidecar + fingerprint + public key — bypassing it requires forging an Ed25519 signature. The trial clock + status computation are independent of the verify path; the audit row on `license.activated` (Plan 04) surfaces any successful activation. |

## Mitigations implemented by this plan

- **T-08-T01, T-08-T02** (trial clock integrity): the trial clock is a UI countdown, not a permission. `status.ts` returns `state: 'expired'` when the clock runs out AND no license is loaded; the IPC gate (Plan 03) blocks procedure capture when the state is `expired`. The clock column can be manipulated locally but it cannot grant license validity.
- **T-08-T03** (transaction atomicity): the new INSERT + audit row run inside the existing wizard transaction; partial failure rolls back.

## Mitigations deferred to later plans

- **T-08-T04** (license activation audit): Plan 04 ships `loadAndVerifyLicense` + the `license.activated` audit row.
- **T-08-IPC-GATE**: Plan 03 wraps every IPC handler — including `procedures.create` — so an `expired` trial blocks new procedures. Plan 02 just sets the state; Plan 03 enforces it at the boundary.
