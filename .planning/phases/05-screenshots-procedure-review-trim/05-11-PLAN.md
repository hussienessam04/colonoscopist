<objective>
Fix the "lightbox shows thumbnail" gap (G-05-14) by aligning the client-side URL composition with the on-disk screenshot layout. The screenshots are stored at `<userData>/data/media/patients/<p>/<proc>/screenshots/<ts>.jpg` (per `paths.ts:screenshotsDir()`), but the MediaServer's `/media/<p>/<proc>/<file>` route only resolves flat filenames — the `screenshots/` segment is rejected by the regex (`[\w.-]+` excludes `/`), and the handler's `path.join` doesn't know about subdirs. Result: the lightbox requests a URL that 404s. The fix extends `MEDIA_ROUTE_RE` to allow an optional literal subdir segment, updates the handler to join the subdir into the resolved path, and adds a defense-in-depth allow-list (`Set(['screenshots'])`) that rejects unknown subdirs with 404. The lightbox URL composition is updated to include the literal `screenshots/` segment.

Purpose: G-05-14 leaves the lightbox useless — the doctor clicks expand, sees a broken `<img>`, and has no way to verify clinical detail at the captured JPEG's native 1280-px resolution. The fix is two small contract changes (regex + handler on the server, URL literal on the client) that mirror the canonical on-disk layout already in use by the screenshots IPC writer. The allow-list ensures the new subdir segment is a deliberate, reviewed contract change.

Output: MediaServer route accepts `/media/<p>/<proc>/screenshots/<file>` and serves the JPEG from `<userData>/data/media/patients/<p>/<proc>/screenshots/<file>`. ScreenshotLightbox URL composition includes `screenshots/`. Tests assert the new URL shape + the allow-list defense + Range request support for the new shape. Flat URLs (`video.mp4`) continue to work — no regression to the `<video>` element.
</objective>
