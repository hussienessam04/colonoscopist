<objective>
Fix the "delete toast but no removal" gap (G-05-13) by adding synchronous local-state removal to both screenshot consumers. The toast store's 5-second delayed IPC + undo window is correct in principle; the bug is that the consumer pages (ProcedureRoom + ProcedureReview) never optimistically remove the thumbnail from the gallery DOM, so the doctor sees the toast but the row stays visible. The fix adds `remove(id)` actions to both `useScreenshotIntake` (ProcedureRoom's hook) and `useProcedures` (ProcedureReview's hook), wires each page's delete handler to call its respective `remove(id)` synchronously before the toast/IPC pipeline, and surfaces IPC failures as a `toast.error` instead of a silent `console.error`. Tests assert the DOM removal + the IPC failure surface + the new hook actions.

Purpose: G-05-13 makes the entire delete affordance feel broken — the doctor clicks ×, sees the toast, but the thumbnail stays, so they click × again thinking nothing happened, then get a duplicate-pending toast. The fix is small (one `remove` action per hook + one line change in each handler + one surface change in the toast store's catch block) but the test surface is what prevents the optimistic-UI class of bug from coming back.

Output: `useScreenshotIntake.remove(id)` + `useProcedures.removeScreenshot(id)` exposed; both delete handlers call their respective remove synchronously; the toast store's `commitDelete` failure surfaces as `toast.error`; new tests assert DOM removal in both pages + the IPC-failure surface + the new `remove` action.
