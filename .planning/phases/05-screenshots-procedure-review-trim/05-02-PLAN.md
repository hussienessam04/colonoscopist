## Trust Boundaries

| Boundary | Description |
|---|---|
| Renderer -> `screenshots.updateAnnotation` IPC | Untrusted renderer sends an annotation; main validates length via `screenshotsUpdateAnnotationInput` zod schema (1 ≤ length ≤ 1000). |
| Renderer -> `useProcedures` hook | The hook is renderer-side; it cannot bypass the IPC validation. The `procedureId` is the route param (renderer-controlled input); the IPC handler validates the procedure exists via `proceduresRepo.get`. |
| Main -> audit_log | `screenshot.annotation_updated` rows are written in the same transaction as the data mutation; metadata is bounded (`{ screenshotId, annotationLength }`). |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|---|---|---|---|---|---|
| T-05-14 | Tampering | Renderer-spoofed `annotation` payload | low | mitigate | `screenshotsUpdateAnnotationInput` enforces `1 ≤ length ≤ 1000`; the audit row stores `annotationLength` not the body (Fix 6). |
| T-05-15 | Denial of Service | Annotation update storm | low | mitigate | The hook serializes `updateAnnotation` calls per screenshot via a simple in-flight lock (the hook returns a rejected promise if a previous update is in flight). |
| T-05-16 | Elevation | Cross-procedure annotation update | low | mitigate | `screenshots.updateAnnotation` is keyed on `id` (the row PK); the IPC handler looks up the row first and rejects `IPC_NOT_FOUND` if the row's procedure_id doesn't match the route's procedureId (defensive check; Phase 1's auth context is the userId-based model). |
| T-05-17 | Information Disclosure | `procedure_notes.list` audit metadata | low | mitigate | The audit row carries `{ procedureId, count }` only — no body content (Fix 6 inheritance from Phase 4). |
